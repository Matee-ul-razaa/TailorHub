## ✅ Fix 2 — Missing DELETE Endpoints

**Problem:** Frontend `StoreContext.js` called `DELETE /api/orders/{id}` and
`DELETE /api/users/{id}`, but neither endpoint existed in the backend.
Clicking delete in the admin dashboard returned 405 Method Not Allowed.

**Files changed:**
- `backend/app/routers_orders.py` — added `DELETE /api/orders/{order_id}`
- `backend/app/routers_users.py` — added `DELETE /api/users/{user_id}` and hardened the existing `PATCH /api/users/{user_id}/role`

**Business rules enforced:**

`DELETE /api/orders/{order_id}` (admin only):
- Returns 403 for non-admin users
- Returns 404 if order doesn't exist
- Refuses to delete `delivered` orders (preserves audit trail)
- Cascades to OrderItems and Payment via SQLAlchemy relationships
- Manually nulls `KhataEntry.order_id` to preserve customer ledger history

`DELETE /api/users/{user_id}` (admin only):
- Returns 403 for non-admin users
- Admins cannot delete themselves while signed in
- Cannot delete the last admin (would lock everyone out)
- Customers with active orders cannot be deleted (preserves order history)
- Delivery users get cleanly removed; their orders' `assigned_to` is nulled
- Their measurements and khata entries are deleted

`PATCH /api/users/{user_id}/role` was hardened against the same last-admin
demotion scenario.

**Verification:** End-to-end test with FastAPI TestClient + SQLite.
13 test cases pass:
```
DELETE /api/orders/{id}:          5 cases pass
DELETE /api/users/{id}:           7 cases pass
PATCH /api/users/{id}/role:       1 case pass (last-admin protection)
```

## Feature 9 — Stock Decrement on Cutting (C5)

**Problem:** Inventory was tracked but never automatically consumed when an order moved into production. Admins had to remember to manually deduct fabric, leading to drift between system and physical stock.

**Files created:**
- `backend/app/services/stock_service.py` — `consume_for_order()` decrements fabric per item, idempotent.
- `backend/alembic/versions/c3d4e5f6a7b8_add_order_inventory_consumed.py` — Migration adding `orders.inventory_consumed_at`.
- `backend/tests/test_stock_service.py` — 7 unit tests covering match, idempotency, warnings, low-stock alerts, substring matching.

**Files modified:**
- `backend/app/models.py` — Added `Order.inventory_consumed_at` (nullable timestamp).
- `backend/app/routers_orders.py` — Wired `consume_for_order()` into status update when transitioning to `cutting`.

**Behaviour:**

1. When an admin/rider PATCHes an order to `cutting`:
   - Each `OrderItem.garment_category` is mapped to a metres-per-unit value (default table in `stock_service`).
   - The matching `inventory_items` row (by name, ILIKE substring) is decremented.
   - If insufficient stock → drains to zero and records a warning (does NOT block the status change).
   - If no inventory row → records a warning (does NOT block).
   - If quantity drops to/below threshold → emits a `inventory.low_stock` notification to all admins.
   - `Order.inventory_consumed_at` is set on first success (idempotency).

2. The full result (consumed lines, warnings, alerts) is recorded in the audit log under action `inventory.consume`.

**Default fabric map (metres per unit):**
| Category | Metres |
|----------|--------|
| `shalwar-kameez` | 4.0 |
| `kurta` | 2.5 |
| `waistcoat` | 1.5 |
| `shirt` | 2.0 |
| `pant` / `trouser` | 1.5 |
| `suit` / `two-piece` | 5.5 |
| `three-piece` | 7.0 |

**Acceptance (C5):**
- [x] Inventory automatically decremented on transition to `cutting`
- [x] Idempotent — re-firing the same status update never double-deducts
- [x] Insufficient stock does NOT block the status update (warns instead)
- [x] Low-stock breaches notify admins via in-app notification
- [x] Audit log captures the full decrement summary
- [x] Stock failures swallowed — never break the parent request
- [x] 7 unit tests pass (matching, idempotency, warnings, low-stock, substring)

**Migration:**
```bash
cd backend && alembic upgrade head
```

**Manual verification:**
```bash

  -d '{"name":"kurta","quantity":20,"unit":"meters","price_per_unit":500,"threshold":10}'

# 2. Create order with kurta items, then move to cutting
curl -X PATCH /api/orders/ORD-XXXXXXXX/status -H "Authorization: Bearer $ADMIN" \
  -d '{"status":"cutting"}'

# 3. Inventory now shows 17.5m (assuming 1 kurta order)
```

**Known limitations / future work:**
- Fabric map is hard-coded in `stock_service.DEFAULT_FABRIC_PER_UNIT_METERS`. Future: a `fabric_requirements` table per product/category.
- No support for multi-fabric garments (e.g. lining + outer). Currently picks one matching inventory row.
- No restoration on order cancellation (stock stays deducted). Add `restore_for_order()` later if needed.

## Feature 10 — Stripe Refund Flow (C6)

**Problem:** Card payments could be captured but never refunded. Admins had to issue refunds manually via the Stripe Dashboard with no local state tracking, leading to drift between Stripe and the app's `Payment.status`.

**Files created:**
- `backend/tests/test_refunds.py` — 14 tests covering authz, validation, full/partial flows, Stripe error handling, webhook reconciliation, idempotency.

**Files modified:**
- `backend/app/routers_payments.py` — Added `POST /api/payments/{order_id}/refund` (admin only). Pydantic schemas: `RefundIn`, `RefundOut`.
- `backend/app/services/webhook_service.py` — Registered `charge.refunded` handler `_handle_charge_refunded()` for refunds initiated outside the app (e.g. Stripe Dashboard).

**Endpoint contract:**
```
POST /api/payments/{order_id}/refund
Authorization: Bearer <admin_token>
Body: {
  "amount": 100.0,        # optional; defaults to full payment amount
  "reason": "requested_by_customer" | "duplicate" | "fraudulent" | null,
  "cancel_order": true    # default; full refund auto-cancels non-delivered orders
}

200 OK:
{
  "payment_id": 42,
  "order_id": "ORD-XXXXXXXX",
  "refund_id": "re_test_1",
  "refunded_amount": 100.0,
  "new_payment_status": "refunded" | "completed",
  "new_order_status": "cancelled" | "confirmed" | ...
}
```

**Business rules enforced:**
| Rule | Result |
|------|--------|
| Non-admin caller | 403 |
| Unknown order | 404 |
| COD payment | 400 (manual handling required) |
| Payment not in `completed` state | 400 |
| Missing `transaction_id` | 400 |
| Refund amount > captured | 400 |
| Stripe API rejects | 502 (local state untouched) |
| Full refund | Payment → `refunded`, Order → `cancelled` (unless `cancel_order=false` or already delivered) |
| Partial refund | Payment stays `completed`, `amount_paid` decremented |

**Webhook reconciliation:**
- `charge.refunded` events from Stripe (e.g. dashboard-initiated refunds) update local `Payment.status` and `Order.amount_paid`.
- Idempotent at two layers:
  1. `webhook_events.event_id` unique constraint blocks duplicate event IDs
  2. `_handle_charge_refunded` no-ops when `Payment.status == refunded`

**Audit + notifications:**
- Every refund writes `payment.refund` to `audit_logs` with full details (`amount`, `is_full`, `reason`, `cancelled_order`, Stripe refund id).
- Customer receives in-app notification (`payment.refunded`) deep-linking to `/tracking/{order_id}`.

**Acceptance (C6):**
- [x] Admin-only endpoint
- [x] Card-only (COD rejected)
- [x] Full + partial refunds supported
- [x] Refund amount validated against captured amount
- [x] Stripe failures return 502, leave local state unchanged
- [x] Full refund auto-cancels order (configurable)
- [x] Webhook handler reconciles externally-initiated refunds
- [x] Audit log + customer notification wired
- [x] 14 unit tests pass

**Known limitations / future work:**
- No partial-then-full state machine: a partial refund leaves payment as `completed`. A second refund call uses the same logic. Could add a `refunded_amount` field to track cumulative refunds.
- No customer-initiated refund request (admin-only). Future: a "request refund" button on customer-facing order page that creates a notification for admins.
